01 / The problem

A plausible answer
is only the beginning.

Everyday problems come with real constraints: the materials on hand, missing measurements, limited tools and actions that need to be reversible. Generic search results rarely account for that specific inventory. An LLM can suggest a convincing plan without evidence that it fits.

I built Possibility Engine to explore options within user-supplied constraints, surface unknowns and check reference support. The work centres on AI systems integration and evaluation: how to retrieve relevant information, enforce output contracts and recognise when an apparently valid answer still falls short.

Application boundaries

The Next.js and TypeScript application separates structured generation through Gemini, embeddings through Ollama, and retrieval/persistence through PostgreSQL. Request and output validation surround provider calls; server-owned citation resolution and owner-scoped saving keep model output from defining trusted references or ownership. Browser fixture tests and the separate live server-harness run exercise different paths, so neither is presented as a verified production user journey.

04 / Live acceptance

The pipeline ran.
The answer still fell short.

Phase 2M · Answer-quality acceptance: FAIL

One bounded, real Gemini scenario planned a removable cardboard tray for eight paper labels. It used actual Ollama embeddings and PostgreSQL retrieval, completed the engine in 7.35 seconds, passed citation and extractive-grounding checks, and persisted the application-accepted result without another provider call.

The final quality assessment was FAIL: the proposal lacked actionable tray geometry and asserted unverified reversibility. The application’s “qualified” label did not establish practical usefulness. I preserved the first output instead of retrying until a favourable answer appeared.

  • Verified: real retrieval, issued citation IDs and three exact reference quotations.
  • Verified: concurrent and repeated saves retained one identical snapshot with owner restrictions.
  • Unresolved: dimensions, cut/fold layout, clip fit, practical feasibility and the categorical reversibility assertion.

The recorded browser tests used fixture mode; the live run used an instrumented server harness. A single live execution does not establish overall reliability. This is an engineering prototype, not a production-ready system.

05 / Engineering decisions

The work behind the interface.

  1. Integration

    Connect real components, then verify them

    Integrated Gemini structured generation, local Ollama embeddings and PostgreSQL/pgvector retrieval. Checked vector dimensions and model identity to avoid mixing incompatible embeddings.

  2. Retrieval evaluation

    Calibrate relevance and measure abstention

    Used separate calibration and frozen test questions to compare retrieval configurations. Selected a small threshold change and reported improved returned-evidence precision alongside reduced recall and false abstentions.

  3. Evidence contracts

    Make citations server-owned

    Introduced stable opaque passage IDs, Zod output validation and server-side source resolution. Unknown IDs and generated URLs cannot become trusted references. Exact claim/quote checks reject unsupported reference assertions.

  4. Orchestration

    Remove a redundant model inspection

    Reused server-prefetched context instead of an extra model-directed inspection. The trade-off is reduced exploratory freedom in exchange for fewer provider calls and potentially lower latency; one run does not prove a general latency gain.

  5. Safety precision

    Diagnose a caution mistaken for an instruction

    A blanket keyword check rejected a harmless structural-safety disclaimer. A narrow whole-warning correction preserved hazard keywords and checks across fields, with adversarial regressions for hidden instructions and ambiguous language.

  6. Reliability & persistence

    Separate execution success from answer quality

    Verified idempotent saves, owner isolation, deadlines and automated regressions. The final live run exposed unsupported structured certainty and missing geometry that passing schema and quotation checks did not catch.

06 / What I learned

AI reliability is an engineering discipline.

Full-Stack Development connects the interface, model contracts, vector search and persistence. AI Engineering adds evaluation, failure diagnosis and a clear distinction between what the system checked and what remains unknown.

This project strengthened my work in LLM Integration, Retrieval-Augmented Generation, Automated Testing and security-minded design. Root-cause investigation was as important as generation: a schema-valid response can still be an inadequate product answer.

07 / Proposed future work

Validate the action, too.

  • Require actionable or explicitly deferred geometry before irreversible cutting advice.
  • Keep reversibility unknown until the evidence and proposed assembly justify it.
  • Expand evidence-backed physical constraints and clarify measurement requirements.
  • Evaluate broader tasks with independently labelled data and supervised human usefulness review.

These are proposed improvements, not implemented functionality.
